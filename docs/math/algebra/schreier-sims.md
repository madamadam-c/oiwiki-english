## Introduction

The **Schreier-Sims algorithm** is an algorithm in computational group theory, named after mathematicians Otto Schreier and Charles Sims. This algorithm can solve many problems in polynomial time, such as finding the order of a finite permutation group, checking whether a given permutation is contained in a given group, and so on. The Schreier-Sims algorithm was first introduced by Sims in 1970 based on the Schreier lemma. In 1981[^knuth-year], Donald Knuth further improved the running time of the algorithm. Later, a faster randomized version of the algorithm was developed. Computer algebra systems (such as GAP and Magma) typically use highly optimized Monte Carlo versions of this algorithm[^monte-carlo].

???+ info "Notation"
    Following the conventions of computational group theory literature, this article uses right action for group actions, which means permutation composition proceeds from left to right. The group actions discussed in this article can all be viewed as permutation actions, although some algorithms also apply to more general group actions. Accordingly, the set of the group action is default to $X=\{1,2,\cdots,n\}$, and its elements are called points. The result of permutation $g$ acting on point $x$ is denoted as $x^g$, and we sometimes say that permutation $g$ moves point $x$ to $x^g$. Finally, under the action of permutation group $G$, the orbit of point $x$ is denoted as $x^G=\{x^g:g\in G\}$, and its stabilizer is denoted as $G_x=\{g\in G:x^g=x\}$. The concept of stabilizer can be extended to a set $B\subseteq X$, and its stabilizer is defined as $G_B=\bigcap_{x\in B}G_x$.

## Overview

The main problem that the Schreier-Sims algorithm attempts to solve is:

-   Given a set $S$ of permutations on a set $X$ of size $n$, how to efficiently store the permutation group $G=\langle S\rangle$ generated by $S$ in a computer, and complete a series of query tasks on this group?

Obviously, such a group $G$ can be very large, far larger than the size of set $X$ and generating set $S$. For example, the symmetric group $S_n=\langle(123\cdots n),(12)\rangle$ on $n$ elements has size $n!$, but it can be generated by only two permutations. Storing every element in the group is impractical.

Similar to using the [Gauss elimination method](../numerical/gauss.md) to construct a [linear basis](../linear-algebra/basis.md) for a vector space, the idea of the Schreier-Sims algorithm is to find a "basis" for a finite permutation group $G$:

1.  The algorithm's input is a generating set $S$ of $G$, containing several permutations;
2.  If group $G$ is non-trivial, we can always find a point $\beta$ whose position changes under the action of group $G$, i.e., $|\beta^G|>1$;
3.  Find the orbit $\Delta=\beta^{G}$ of point $\beta$, and for each point $\delta\in\Delta$ in the orbit, find a permutation $t_{\delta}$ in group $G$ that can move point $\beta$ to $\delta$;
4.  Find a generating set $S'$ for the stabilizer $G_{\beta}$ of point $\beta$;
5.  Recursively call this algorithm on $G'=\langle S'\rangle$ until we obtain the trivial group $\{e\}$.

The rationality of this approach is that the stabilizer $G_{\beta}$ of point $\beta$ is a subgroup of group $G$, and its (right) cosets form a partition of group $G$, and these cosets are in one-to-one correspondence with the orbit $\beta^G$ of point $\beta$. The permutations $t_{\delta}$ obtained in step 3 are the representatives of these cosets. This set of coset representatives $T$ is called the **transversal** (or coset representative system) of the stabilizer $G_{\beta}$. In other words, every element $g$ in group $G$ corresponds uniquely to a pair $(h,t)\in G_\beta\times T$, and $g=ht$. Therefore, as long as we can store the subgroup $G_{\beta}$ and the corresponding transversal $T$, we can store the entire group $G$. However, the problem of storing the subgroup $G_{\beta}$ has already been solved—by recursively calling the algorithm.

Of course, there are many details to sort out in the implementation of the algorithm, which is the main content of this article. But before that, we should examine the results obtained after calling the algorithm, see how the algorithm stores the group, and what query problems it can solve. To do this, we need to clarify some concepts.

### Stabilizer Chain

Suppose we call this algorithm on group $G=\{S\}$, and it performs $k$ iterations; and in the $i$-th iteration, the input is the set of permutations $S^{(i-1)}$, the point found is $\beta_i$, the transversal obtained is $T_i$, and the generating set for the stabilizer is $S^{(i)}$. If we denote $G^{(i)}=\langle S^{(i)}\rangle$. Then the algorithm actually obtains a chain of subgroups

$$
G=G^{(0)}> G^{(1)}>\cdots> G^{(k-1)}> G^{(k)}=\{e\}.
$$

Moreover, each subgroup in the chain is a stabilizer

$$
G^{(i)}=G_{\beta_1,\cdots,\beta_i}.
$$

Thus, the Schreier-Sims algorithm can be seen as computing such a **stabilizer chain**.

### Base and Strong Generating Set

If a subset $B$ of set $X$ satisfies $G_B=\{e\}$, then $B$ is called a **base** of the permutation group $G$. Obviously, the algorithm above obtains a base $B=\{\beta_1,\cdots,\beta_k\}$. This means that the result of permutation $g\in G$ acting on these points uniquely determines this permutation in group $G$. Moreover, this base output by the algorithm also satisfies the condition

$$
G^{(i-1)}=G_{\beta_1,\cdots,\beta_{i-1}}>G_{\beta_1,\cdots,\beta_{i-1},\beta_i}=G^{(i)}.
$$

That is, each point in the base carries effective information about the elements in the group. Such a base is called **nonredundant**. The algorithm always outputs a nonredundant base. The stabilizer chain corresponding to such a base is strictly decreasing.

At the same time, the union of the generating sets obtained by the algorithm

$$
\bar S=\bigcup_{i=0}^kS_i
$$

is also a generating set of group $G$, and we have $\langle\bar S\cap G^{(i)}\rangle = G^{(i)}$. A generating set satisfying this condition is called a **strong generating set** of group $G$ relative to base $B$. Thus, the Schreier-Sims algorithm can also be seen as computing the **base and strong generating set** (BSGS) of group $G$. This formulation is equivalent to the stabilizer-chain formulation, and this article does not distinguish between them.

The algorithm also obtains a series of orbits $\Delta_i=\beta_{i}^{G^{(i-1)}}$ and corresponding transversals $T_i$. These orbits are called the **fundamental orbits** of group $G$. When this article mentions the stabilizer chain or base and strong generating set of group $G$, it is always assumed that the corresponding fundamental orbits and transversals have been computed together.

### Data Structure

This article will provide a series of pseudocode. In the pseudocode, the stabilizer chain (or base and strong generating set) of a group is stored in a data structure $C$:

$$
C=(S,\Delta,T,C').
$$

The data members of this structure are: the generating set $S$ of the current group, the fundamental orbit $\Delta$, the corresponding transversal $T$, and the stabilizer $C'$ stored as a nested substructure. Of course, $C'$ is also such a structure. The entire group is actually stored in a layered structure, with each layer describing a group in the stabilizer chain. The innermost layer is an empty struct, representing $G^{(k)}=\{e\}$.

In the pseudocode, the members of this data structure can be accessed via $C.generators$, $C.orbit$, $C.transversal$, and $C.next$ respectively. The first element of the orbit $C.orbit[0]$ is default to the base point $\beta$, and the corresponding coset representative $C.transversal[\beta]$ is default to the identity transformation $e$. Note that although array index access is used here to access elements in the orbit and transversal, they may not necessarily be stored as arrays; rather, they should be understood as providing methods to access the first element of the orbit and to query the corresponding coset representative by a point in the orbit. The specific implementation details will be discussed later.

### Applications

After obtaining the base and strong generating set of a group, we can solve a series of query problems about the group. Among them, the most basic, and also the most common in programming contests, are querying the order of the group and determining whether a permutation belongs to a given group.

#### Order of a Group

If we know the base and strong generating set of group $G$, then applying Lagrange's theorem and the orbit-stabilizer theorem, the order of group $G$ can be computed as

$$
|G|=\prod_{i=1}^k[G^{(i-1)}:G^{(i)}]=\prod_{i=1}^k[G^{(i-1)}:G^{(i-1)}_{\beta_i}]=\prod_{i=1}^k|T_i|.
$$

Therefore, we can obtain the order of group $G$ by multiplying the sizes of all transversals $T_i$ (or equivalently, the lengths of the fundamental orbits $\Delta_i$).

#### Membership Testing

Knowing the base and strong generating set of group $G$, we can also determine whether a given permutation $h$ belongs to group $G$. This is called the **membership testing** problem.

This problem can be solved recursively. To determine $h\in G^{(i-1)}$, we must first find the representative $t\in T_i$ of the coset of $G^{(i)}$ containing $h$. If we can find it, then let $h'=ht^{-1}$, and we have $h=h't$ and $h\in G^{(i-1)}$ is equivalent to $h'\in G^{(i)}$; the problem reduces to determining $h'\in G^{(i)}$. If we cannot find such $t$, or if we have recursed to $G^{(k)}=\{e\}$ but $h\neq e$, we can conclude that $h\notin G$. In fact, this process not only determines whether $h\in G$, but also, in the case $h\in G$, can express $h$ as a product of a series of coset representatives $t_k\cdots t_2t_1$, where $t_i\in T_i$. Such a representation exists and is unique for elements in group $G$. This again proves that the formula for the order of the group above is correct.

Now we write this process as follows in pseudocode:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{MembershipTest}(C,h):\\
\textbf{Input. }\textrm{A stabilizer chain }C\textrm{ for a group }G\textrm{ and a permutation }h.\\
\textbf{Output. }\textrm{Whether }h\in G.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \textbf{while }C\textrm{ is not empty }\\
2  & \qquad \beta \leftarrow C.orbit[0]\\
3  & \qquad \delta \leftarrow \beta^h\\
4  & \qquad \textbf{if }\delta\in C.orbit\textbf{ then}\\
5  & \qquad \qquad t \leftarrow C.transversal[\delta]\\
6  & \qquad \qquad h \leftarrow ht^{-1}\\
7  & \qquad \textbf{else }\\
8  & \qquad \qquad \textbf{return }\textrm{false}\\
9  & \qquad \textbf{end if}\\
10 & \qquad C \leftarrow C.next\\
11 & \textbf{end while}\\
12 & \textbf{return }h=e
\end{array}
\end{array}
$$

As we will see later, the membership testing problem is also an important component in the implementation of the Schreier-Sims algorithm discussed in this article.

## Computing Orbits, Transversals, and Stabilizers

To implement the Schreier-Sims algorithm, we first need to solve the following subproblem:[^orbit-algo]

-   Given a generating set $S$ of group $G$ and a point $\beta$, how to compute the orbit $\beta^G$, the corresponding transversal $T$, and a generating set for the stabilizer $G_\beta$?

This is the problem to be solved in this section.

### Storing Orbits and Transversals

To compute the orbit and transversal, we can simply perform a search. The pseudocode is as follows:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{OrbitTransversal}(S,\beta):\\
\textbf{Input. }\textrm{A generating set }S\textrm{ for a group }G\textrm{ and a point }\beta.\\
\textbf{Output. }\textrm{The orbit }\Delta=\beta^G\textrm{ and the transversal }T.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \Delta \leftarrow [\beta]\\
2  & T[\beta] \leftarrow e\\
3  & \textbf{for }\delta\in\Delta\\
4  & \qquad \textbf{for }s\in S\\
5  & \qquad \qquad \gamma \leftarrow \delta^s\\
6  & \qquad \qquad \textbf{if }\gamma\notin\Delta\textbf{ then}\\
7  & \qquad \qquad \qquad\textrm{append }\gamma\textrm{ to }\Delta\\
8  & \qquad \qquad \qquad T[\gamma] \leftarrow T[\delta]\cdot s\\
9  & \qquad \qquad \textbf{end if}\\
10 & \qquad \textbf{end for}\\
11 & \textbf{end for}\\
12 & \textbf{return }\Delta, T
\end{array}
\end{array}
$$

In actual implementation, both breadth-first search and depth-first search can be used. The number of states visited during the search is $|S||T|$, and as long as we can store the orbit and transversal reasonably, the time complexity is completely acceptable.

Since in the context of permutation groups, an orbit is at most a set of $n$ points, to efficiently perform lookup and addition operations, we can use a boolean array or an unordered set. In this way, both operations have $O(1)$ time complexity, and the overall space consumption is $O(n)$. Of course, depending on the implementation of the transversal, additional marking of the position of the first element may be needed.

The problem is what data structure to use to store the corresponding transversal $T$.

#### Direct Storage

The simplest method, of course, is to directly store each element $t$ in the transversal $T$. A single permutation stored in [one-line notation](../permutation.md#one-line-notation) requires exactly $n$ space, so storing such a transversal has space complexity $O(|T|n)$. The benefit of this is that accessing a single coset representative has $O(1)$ time complexity, at the cost of $O(|T|n)$ time complexity for the initial computation of these coset representatives.

#### Schreier Tree

Another common approach is to implement a tree structure to store the transversal. It is called a **Schreier tree** (or Schreier vector)[^schreier-vector]. It takes $\beta$ as the root, and the elements $\delta$ in the orbit $\Delta$ as vertices. Each time a new vertex $\gamma=\delta^s$ is obtained during the search, we connect an edge from the old vertex $\delta$ to the new vertex $\gamma$, and on the edge we record the index (or pointer) of the permutation $s$ in the generating set $S$. Since the generating set is already stored, the additional space complexity for storing the transversal is $O(|T|)$. For cases where $n$ is very large, this can effectively save space, and the initial computation has complexity $O(|T|)$. However, the side effect is that each time we need to obtain a coset representative, we need to traverse the path from the vertex to the root, recalculating the coset representative, so the time complexity highly depends on the depth of the Schreier tree. In general cases, the tree depth can reach $O(n)$.

In actual implementation, we need to weigh the time and space complexity of the algorithm based on the actual situation. For situations that may be encountered in programming contests, $n$ is usually not large, space is sufficient, and time complexity is often the bottleneck. As we will see later, the most time-consuming step of the Schreier-Sims algorithm requires multiple accesses to coset representatives, so using direct storage is often better. However, for some applications, $n$ may be very large and storage space may be more constrained, in which case it may be necessary to use the Schreier tree method to store the transversal. For such cases, to avoid excessively deep Schreier trees, researchers have proposed many methods to reconstruct a shallow Schreier tree when the tree becomes too deep. Interested readers can refer to the references at the end of this article.

In pseudocode, this article will not distinguish between the specific implementations of the transversal, but only assumes that the data structure storing the transversal $T$ implements operations to access and modify the corresponding coset representative $T[\delta]$ for an orbit element $\delta\in\Delta$.

### Schreier Lemma

After obtaining the orbit $\beta^G$ and transversal $T$, the Schreier lemma provides a method to obtain a generating set for the stabilizer $G_\beta$.

???+ note "Schreier Lemma"
    Let group $G=\langle S\rangle$ have a subgroup $H\le G$. Let $T$ be a (right) transversal of subgroup $H$, and $e\in T$[^schreier-lemma-unity], and denote the representative of the coset containing $g\in G$ as $t\in T$ as $\overline g$. Then the set
    
    $$
    U=\{ts(\overline{ts})^{-1}:t\in T,s\in S\}
    $$
    
    is a generating set of subgroup $H$. Its elements are called **Schreier generators** of subgroup $H$.

??? note "Proof"
    First, according to the definition of coset representatives, $ts(\overline{ts})^{-1}\in H$ holds for all $t\in T,s\in S$, so $\langle U\rangle\subseteq H$.
    
    Conversely, for any $h\in H$, since $S$ is a generating set of $G\ge H$, there must exist a sequence $s_i\in S\cup S^{-1}$ such that
    
    $$
    h=s_1s_2\cdots s_r
    $$
    
    holds. Let $t_1=e$, and recursively define $t_{i+1}=\overline{s_it_i}\in T$, then we have
    
    $$
    \begin{aligned}
    h&=\left(t_1s_1t_2^{-1}\right)\left(t_2s_2t_3^{-1}\right)\cdots(t_rs_rt_{r+1})^{-1}t_{r+1}.
    \end{aligned}
    $$
    
    And for each $i=1,2,\cdots,r$, we have $t_is_it_{i+1}^{-1}=t_is_i(\overline{t_is_i})^{-1}\in U\cup U^{-1}\subseteq H$, so $t_{r+1}\in H$. But $H\cap T=\{e\}$, so $t_{r+1}=e$. This shows that any $h\in H$ can be written as a product of a sequence of $u_i=t_is_it_{i+1}^{-1}\in U\cup U^{-1}$, that is, $U$ generates $H$.

Since the subgroup corresponding to transversal $T$ is the stabilizer $G_\beta$, after obtaining the transversal $T$ and combining with the generating set $S$ of group $G$, we can obtain a generating set for the stabilizer $G_\beta$.

### Algorithm

With just a slight modification to the pseudocode above, we can obtain the generating set for the corresponding stabilizer while computing the orbit and transversal:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{OrbitTransversalStabilizer}(S,\beta):\\
\textbf{Input. }\textrm{A generating set }S\textrm{ for a group }G\textrm{ and a point }\beta.\\
\textbf{Output. }\textrm{The orbit }\Delta=\beta^G\textrm{, the transversal }T\textrm{, and a}\\
\qquad\textrm{ generating set }S'\textrm{ for the stabilizer }G_\beta.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \Delta \leftarrow [\beta]\\
2  & T[\beta] \leftarrow e\\
3  & S' \leftarrow [e]\\
4  & \textbf{for }\delta\in\Delta\\
5  & \qquad \textbf{for }s\in S\\
6  & \qquad \qquad \gamma \leftarrow \delta^s\\
7  & \qquad \qquad \textbf{if }\gamma\notin\Delta\textbf{ then}\\
8  & \qquad \qquad \qquad\textrm{append }\gamma\textrm{ to }\Delta\\
9  & \qquad \qquad \qquad T[\gamma] \leftarrow T[\delta]\cdot s\\
10 & \qquad \qquad \textbf{else} \\
11 & \qquad \qquad \qquad \textrm{append }T[\delta]\cdot s\cdot T[\gamma]^{-1}\textrm{ to }S'\\
12 & \qquad \qquad \textbf{end if}\\
13 & \qquad \textbf{end for}\\
14 & \textbf{end for}\\
15 & \textbf{return }\Delta, T, S'
\end{array}
\end{array}
$$

In the pseudocode, for each pair $(\delta,s)$, only when no new element is produced in the orbit is $t_\delta st_{\delta^s}^{-1}$ a new Schreier generator; otherwise, it is the identity transformation $e$. Therefore, the algorithm actually generates at most

$$
|S||T|-(|T|-1) = |S|(|T|-1)+1
$$

Schreier generators (including the initial identity transformation). For general cases, this upper bound is tight.[^upper-bound] However, for finite groups that we actually need to process, this upper bound is quite loose: most of these newly obtained Schreier generators are either duplicates of previously obtained generators, or can be composed from previous generators.

Since the basic workflow of the Schreier-Sims algorithm can be implemented as recursively calling the above algorithm for computing orbits and stabilizers, we have already obtained a naive implementation of the Schreier-Sims algorithm at this point. However, without filtering, the growth rate of the size of Schreier generators is exponential: repeatedly applying $O(|S_{i}|)=O(|S_{i-1}||T_i|)$, we can see that the generating set of the innermost stabilizer will reach $O(|S||G|)$. This is obviously absurdly inefficient, because the innermost stabilizer is $\{e\}$.

Sims' work provides a method to limit the growth rate of the size of Schreier generators, which can guarantee that the final strong generating set $\bar S$ has size $O(n^2)$. This allows computing the base and strong generating set in polynomial time.

## The Schreier-Sims Algorithm

To solve the above problem, this section discusses an incremental implementation of the Schreier-Sims algorithm, which obtains a strong generating set of size $O(n^2)$.

### Filtering

The core optimization of the Schreier-Sims algorithm over the naive algorithm is quite simple: it requires that before adding any Schreier generator to the generating set of the stabilizer, it must first go through **filtering**. Filtering means first determining whether the new Schreier generator already exists in the subgroup generated by the existing generators, and then only adding those that do not yet exist. To do this, we only need to use the membership testing algorithm $\textrm{MembershipTest}(C,h)$ from earlier.

However, the precondition for being able to do this is that, based on the Schreier generators already generated by the current group, the stabilizer chain (or base and strong generating set) of the group they generate has long been constructed. This means that each time a new Schreier generator is added to the generating set of the stabilizer, we need to dynamically maintain the inner stabilizer chain for subsequent filtering. However, inserting one generator at the current layer may produce multiple Schreier generators, which may cause multiple updates to the inner structure; and each update of the inner structure may trigger multiple updates of the even more inner structure.

It seems that the exponential explosion problem mentioned earlier still exists. Actually, it doesn't. Because we have done filtering in advance, only when the generator to be added really causes expansion of a certain layer's structure will that layer's structure be updated. This shows that the number of times a single layer's structure is updated is actually equal to the number of times the group stored in that layer strictly grows. However, a group of size $|G|$ has a subgroup chain of length at most $\log|G|$; because Lagrange's theorem guarantees that each time the subgroup chain length increases by one, the group size at least doubles. This shows that a single layer's structure is updated at most $\log|G|$ times, so the final size of the strong generating set $\bar S$ is $|B|\log|G|$.

This estimate can be further improved. Since the group $G$ here is known to be a subgroup of the symmetric group $S_n$ on $n$ elements, the length of the subgroup chain of $G$ does not exceed that of $S_n$. It can be proven[^subgroup-chain] that the length of a strictly increasing subgroup chain of $S_n$ does not exceed $3n/2$. This shows that the number of times a single layer's structure is updated is actually $O(n)$. Obviously, the size of the base does not exceed $n$. Therefore, the final size of the strong generating set $\bar S$ is $O(n^2)$.

The filtering method mentioned here was proposed by Sims, and is also called the Sims filter. There is also a more complex filtering method proposed by Jerrum, also called the [Jerrum filter](https://groupprops.subwiki.org/w/index.php?title=Jerrum%27s_filter), which can guarantee that the obtained strong generating set has size $O(n)$. Interested readers can study it on their own.

For the filtering process, there is a small optimization: in the implementation of $\textrm{MembershipTest}(C,h)$, instead of outputting a boolean value, we output the final "sifted"[^siftee] $h$ (i.e., use $\textbf{return }h$ instead of lines $10$ and $14$ in the pseudocode). If the sifted $h\neq e$, then membership testing fails, and we can directly add the sifted $h$ rather than the original $h$ to the current layer. Here, the sifted $h$ has already had several coset representative factors removed, so it moves fewer elements, thus reducing local computation. This optimization has no effect on the overall complexity.

### Procedure

Now we can describe the specific procedure of the Schreier-Sims algorithm: first, initialize an empty structure $C$ to store the group's stabilizer chain. Then, add the generators in the generating set $S$ to the structure one by one. The final structure $C$ is the stabilizer chain of group $\langle S\rangle$. The pseudocode is as follows:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{SchreierSims}(S):\\
\textbf{Input. }\textrm{A generating set }S\textrm{ for a group }G.\\
\textbf{Output. }\textrm{The stabilizer chain }C\textrm{ for the group }G.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & C \leftarrow []\\
2  & \textbf{for }s\in S\\
3  & \qquad C \leftarrow \textrm{Extend}(C,s)\\
4  & \textbf{end for}\\
5  & \textbf{return }C
\end{array}
\end{array}
$$

The core of the algorithm is adding a new generator $s$ to the current $C$, that is, the subroutine $\textrm{Extend}(C,s)$. As mentioned earlier, both before and after adding permutation $s$, we need to ensure that $C$ is a stabilizer chain. Thus, before adding permutation $s$, we can first do filtering. If we find that $s$ is not in the existing group, we **incrementally** compute the orbit, transversal, and Schreier generators. Here, "incrementally" means not recalculating what has already been calculated. Only in this way can we ensure the correct complexity.

Consider how to transform $\textrm{OrbitTransversalStabilizer}(S,\beta)$ into an incremental version. The algorithm searches the state space $\Delta\times S$. After adding a new generator $s$, the state space becomes $\Delta'\times\left(S\cup\{s\}\right)$. The difference between the two is

$$
\left(\Delta\times\{s\}\right)\cup\left((\Delta'\setminus\Delta)\times \left(S\cup\{s\}\right)\right).
$$

This means that when adding a new generator $s$, we first need to compute the combinations of the new generator $s$ with the old orbit and corresponding coset representatives; if new orbit elements are obtained in this process, we then consider the combinations of these elements with all generators (both old and new); the process repeats until the orbit no longer extends.

The pseudocode for adding a permutation $g$ to structure $C$ is as follows:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{Extend}(C,g):\\
\textbf{Input. }\textrm{A stabilizer chain }C\textrm{ for the group generated by }S\textrm{ and a}\\
\qquad \textrm{permutation }g.\\
\textbf{Output. }\textrm{A stabilizer chain }C\textrm{ for the group generated by }S\cup\{g\}.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \textbf{if }\textrm{MembershipTest}(C,g)\textrm{ is passed}\textbf{ then}\\
2  & \qquad \textbf{return }C\\
3  & \textbf{end if}\\
4  & \textbf{if }C\textrm{ is empty}\textbf{ then}\\
5  & \qquad \beta \leftarrow \textrm{an element moved by }g\\
6  & \qquad C.orbit[0] \leftarrow \beta \\
7  & \qquad C.transversal[\beta] \leftarrow e\\
8  & \textbf{end if}\\
9  & \textrm{append }g\textrm{ to }C.generators\\
10  & \Delta \leftarrow C.orbit \\
11 & \textbf{for }\delta\in\Delta \\
12 & \qquad \gamma \leftarrow \delta^g \\
13 & \qquad \textbf{if }\gamma\notin C.orbit\textbf{ then}\\
14 & \qquad \qquad \textrm{append }\gamma\textrm{ to }C.orbit\\
15 & \qquad \qquad C.transversal[\gamma] \leftarrow C.transversal[\delta]\cdot g\\
16 & \qquad \textbf{else}\\
17 & \qquad \qquad s'\leftarrow C.transversal[\delta]\cdot g\cdot C.transversal[\gamma]^{-1}\\
18 & \qquad \qquad C.next \leftarrow \textrm{Extend}(C.next, s')\\
19 & \qquad \textbf{end if}\\
20 & \textbf{end for} \\
21 & \textbf{for }\delta\in C.orbit\setminus\Delta \\ 
22 & \qquad \textbf{for }s\in C.generators \\
23 & \qquad \qquad \gamma \leftarrow \delta^s \\
24 & \qquad \qquad \textbf{if }\gamma\notin C.orbit\textbf{ then}\\
25 & \qquad \qquad \qquad\textrm{append }\gamma\textrm{ to }C.orbit\\
26 & \qquad \qquad \qquad C.transversal[\gamma] \leftarrow C.transversal[\delta]\cdot s\\
27 & \qquad \qquad \textbf{else}\\
28 & \qquad \qquad \qquad s'\leftarrow C.transversal[\delta]\cdot s\cdot C.transversal[\gamma]^{-1}\\
29 & \qquad \qquad \qquad \textrm{Extend}(C.next, s')\\
30 & \qquad \qquad \textbf{end if}\\
31 & \qquad \textbf{end for}\\
32 & \textbf{end for} \\
33 & \textbf{return }C
\end{array}
\end{array}
$$

This gives us the complete Schreier-Sims algorithm.

### Another Implementation

The above implementation is already correct, but lines $12\sim19$ and $23\sim30$ are somewhat repetitive. Based on this, Knuth proposed a recursive implementation in his paper, which is more concise. His approach is to treat this repetitive part as updating the transversal (and orbit). Each time we update the transversal, we combine it with all generators, and depending on whether a new coset representative is produced, we decide whether to recursively call itself or the generator-adding procedure. The pseudocode is as follows:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{Extend}(C,g):\\
\textbf{Input. }\textrm{A stabilizer chain }C\textrm{ for the group generated by }S\textrm{ and a}\\
\qquad \textrm{permutation }g.\\
\textbf{Output. }\textrm{A stabilizer chain }C\textrm{ for the group generated by }S\cup\{g\}.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \textbf{if }\textrm{MembershipTest}(C,g)\textrm{ is passed}\textbf{ then}\\
2  & \qquad \textbf{return }C\\
3  & \textbf{end if}\\
4  & \textbf{if }C\textrm{ is empty}\textbf{ then}\\
5  & \qquad \beta \leftarrow \textrm{an element moved by }g\\
6  & \qquad C.orbit[0] \leftarrow \beta \\
7  & \qquad C.transversal[\beta] \leftarrow e\\
8  & \textbf{end if}\\
9  & \textrm{append }g\textrm{ to }C.generators\\
10 & \textbf{for }t\in C.transversal\\
11 & \qquad \textrm{ExtendTranserversal}(C,t\cdot g)\\
12 & \textbf{end for}\\
13 & \textbf{return }C
\end{array}
\\
\textbf{Sub-Algorithm }\textrm{ExtendTranserversal}(C,t):\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \beta \leftarrow C.orbit[0]\\
2  & \gamma \leftarrow \beta^t\\
3  & \textbf{if }\gamma\notin C.orbit\textbf{ then}\\
4  & \qquad \textrm{append }\gamma\textrm{ to }C.orbit\\
5  & \qquad C.transversal[\gamma] \leftarrow t\\
6  & \qquad \textbf{for }s\in C.generators\\
7  & \qquad \qquad \textrm{ExtendTranserversal}(C,t\cdot s)\\
8  & \qquad \textbf{end for}\\
9  & \textbf{else}\\
10 & \qquad s' \leftarrow t\cdot C.transversal[\gamma]^{-1}\\
11 & \qquad \textrm{Extend}(C.next,s')\\
12 & \textbf{end if}
\end{array}
\end{array}
$$

Comparing this pseudocode with that of the previous section, we can see that it is correct. Moreover, their complexities are the same.

### Complexity Analysis

To analyze the complexity of the Schreier-Sims algorithm, we need some notation. Let the length of the permutation be $n$, and the size of the generating set be $|S|=m$. Let the length of the (nonredundant) base obtained be $|B|$. Moreover, let the number of generators in the $i$-th layer from the outside be $|S_{i-1}|$, and the size of the transversal (or the length of the orbit) be $|T_i|$. Below we analyze the time complexity required by the incremental implementation of the Schreier-Sims algorithm above. The algorithm consists of two main parts: filtering, and the computation of orbits, transversals, and Schreier generators.

Both the initially input generators and the Schreier generators obtained in the algorithm need to be filtered, so the total number of filtering executions is $O(\sum_{i=1}^{|B|}|S_{i-1}||T_i|+|S|)$. Single filtering needs to compute permutation products with $O(|B|)$ coset representatives. Let the time to compute a product with a single coset representative be $\tau$. When storing coset representatives directly, $\tau\in O(n)$; when using a Schreier tree to store coset representatives, $\tau\in O(n^2)$. The total time complexity of the filtering process is $O(\tau|B|\sum_{i=1}^{|B|}|S_{i-1}||T_i|+\tau|B||S|)$.

For the computation of orbits and related information, since it is an incremental implementation, each pair $(\delta,s)\in\Delta_i\times S_{i-1}$ in the state space is computed at most once. For the computation of orbits and transversals, depending on the storage method, the time complexity for computing a single coset representative may be $O(n)$ or $O(1)$. However, in any case, it does not exceed the complexity of computing Schreier generators. When stored directly, it is $O(n)$; when using a Schreier tree, it is $O(n^2)$. Comparing with the total time complexity of the filtering process, we find that the time for computing this information does not exceed the time required for filtering. Therefore, the time complexity of the Schreier-Sims algorithm is $O(\tau|B|\sum_{i=1}^{|B|}|S_{i-1}||T_i|+\tau|B||S|)$ as obtained in the previous paragraph.

As for space complexity, the final data structure stores $O(\sum_{i=1}^{|B|}|S_{i-1}|)$ generators and $O(\sum_{i=1}^{|B|}|T_i|)$ coset representatives. If using direct storage, both generators and coset representatives require $O(n)$ space; if using a Schreiner tree, generators require $O(n)$ space, while coset representatives only require $O(1)$ space.

As explained earlier, the length of a strictly increasing subgroup chain in the symmetric group $S_n$ is $O(n)$, which applies to both $|B|$ and $|S_i|$. Therefore, using direct storage for transversals, the Schreier-Sims algorithm has time complexity $O(n^5+mn^2)$ and space complexity $O(n^3)$. Of course, for the case where $\log|G|\in O(n)$, a better estimate is time complexity[^knuth-complexity] $O(n^2\log^3|G|+mn\log|G|)$ and space complexity $O(n^2\log|G|)$. For random generating sets, actual testing shows that the algorithm's complexity is significantly lower than $\Theta(n^5)$, roughly $\Theta(n^4)$.

Although using a Schreiner tree introduces an extra factor of $n$ in time complexity compared to direct storage, for cases where $n$ is very large but the group itself is much smaller than the symmetric group $S_n$, its space complexity is $O(n\log^2|G|)$, far less than $O(n^2\log|G|)$ for direct storage. However, in programming contests, it is rare to encounter situations where using a Schreiner tree for storage is better.
