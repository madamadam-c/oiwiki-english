    Standard Mo's Algorithm

    Form

    Assume 𝑛 =𝑚n=m. For range query problems on a sequence, if the answer for [𝑙,𝑟][l,r] can be extended in 𝑂(1)O(1) to the answers for [𝑙 −1,𝑟],[𝑙 +1,𝑟],[𝑙,𝑟 +1],[𝑙,𝑟 −1][l−1,r],[l+1,r],[l,r+1],[l,r−1] (that is, intervals adjacent to [𝑙,𝑟][l,r]), then all query answers can be found in 𝑂(𝑛√𝑛)O(nn) time.

    Explanation

    After processing offline, sort the queries and handle them in order. Brute-force transition from the previous interval's answer to the next interval's answer by moving one step at a time.

    Sorting Method

    For interval [𝑙,𝑟][l,r], sort in increasing order by the block number containing 𝑙l as the first key, and by 𝑟r as the second key.

void solve() {
  BLOCK_SIZE = int(ceil(pow(n, 0.5)));
  sort(querys, querys + m);
  for (int i = 0; i < m; ++i) {
    const query &q = querys[i];
    while (l > q.l) move(--l, 1);
    while (r < q.r) move(++r, 1);
    while (l < q.l) move(l++, -1);
    while (r > q.r) move(r--, -1);
    ans[q.id] = nowAns;
  }
}

    Complexity Analysis

    The following discussion assumes 𝑛n and 𝑚m are of the same order.

    First, consider the blocking step. Its time complexity is 𝑂(√𝑛 ⋅√𝑛log⁡√𝑛 +𝑛log⁡𝑛) =𝑂(𝑛log⁡𝑛)O(n⋅nlog⁡n+nlog⁡n)=O(nlog⁡n).

    Next comes the essence of Mo's algorithm. We will prove its time complexity is 𝑂(𝑛√𝑛)O(nn) using an intuitive elementary method.

    Proof

    Proof: Let the maximum value of 𝐿L in each block be max1,max2,max3,⋯,max⌈√𝑛⌉max1,max2,max3,⋯,max⌈n⌉.

    From the first sorting key, we know max1 ≤max2 ≤⋯ ≤max⌈√𝑛⌉max1≤max2≤⋯≤max⌈n⌉.

    Clearly, brute-forcing the first query in each block costs 𝑂(𝑛)O(n) time.

    Consider the worst case. In every block, the maximum value of 𝑅R is 𝑛n, and each modification operation changes 𝐿L from max𝑖−1maxi−1 to max𝑖maxi or from max𝑖maxi to max𝑖−1maxi−1.

    Consider 𝑅R: since 𝑅R has already been sorted within a block, modifying it throughout the same block costs 𝑂(𝑛)O(n) time. Across all blocks, this is 𝑂(𝑛√𝑛)O(nn).

    Now focus on 𝐿L: since each change costs 𝑂(max𝑖 −max𝑖−1)O(maxi−maxi−1), the time complexity within the same block is 𝑂(√𝑛 ⋅(max𝑖 −max𝑖−1))O(n⋅(maxi−maxi−1)).

    Combining the time complexity of 𝐿L over all blocks gives:

    The total time complexity for 𝐿L is

    𝑂(√𝑛(max1−1)+√𝑛(max2−max1)+√𝑛(max3−max2)+⋯+√𝑛(max⌈√𝑛⌉−max⌈√𝑛⌉−1))=𝑂(√𝑛⋅(max1−1+max2−max1+max3−max2+⋯+max⌈√𝑛⌉−1−max⌈√𝑛⌉−2+max⌈√𝑛⌉−max⌈√𝑛⌉−1))=𝑂(√𝑛⋅(max⌈√𝑛⌉−1))O(n(max1−1)+n(max2−max1)+n(max3−max2)+⋯+n(max⌈n⌉−max⌈n⌉−1))=O(n⋅(max1−1+max2−max1+max3−max2+⋯+max⌈n⌉−1−max⌈n⌉−2+max⌈n⌉−max⌈n⌉−1))=O(n⋅(max⌈n⌉−1))

    (telescoping sum)

    From the problem, max⌈√𝑛⌉max⌈n⌉ is at most 𝑛n, so the total time complexity for 𝐿L is 𝑂(𝑛√𝑛)O(nn) in the worst case.

    In summary, the time complexity of Mo's algorithm is 𝑂(𝑛√𝑛)O(nn).

    However, for other values of 𝑚m, such as 𝑚 <𝑛m<n, the blocking method needs to change to become more optimal.

    How should we choose the block size?

    Let the block length be 𝑆S. For any number of queries in the same block, the movement distance is 𝑛n. There are 𝑛𝑆nS blocks, so the total number of moves is 𝑛2𝑆n2S. Since movement may cross blocks, we also add a complexity of 𝑚𝑆mS. The total complexity is 𝑂(𝑛2𝑆+𝑚𝑆)O(n2S+mS). To minimize this value, make the two terms as equal as possible. We find that choosing 𝑆S as 𝑛√𝑚nm is optimal, giving complexity 𝑂⎛⎜ ⎜ ⎜ ⎜ ⎜⎝𝑛2𝑛√𝑚+𝑚(𝑛√𝑚)⎞⎟ ⎟ ⎟ ⎟ ⎟⎠ =𝑂(𝑛√𝑚)O(n2nm+m(nm))=O(nm).

    In fact, if the block length is set inaccurately, the time complexity of Mo's algorithm can be greatly affected. For example, if 𝑚m is of the same order as √𝑛n and the block length is mistakenly set to √𝑛n, it is easy to construct data that makes the time complexity 𝑂(𝑛√𝑛)O(nn) instead of the correct 𝑂(𝑛5/4)O(n5/4).

    Mo's algorithm looks very brute-force largely because its block-based sorting method appears crude. One might think of sorting all intervals using a seemingly more refined method. For example, treat all intervals [𝑙,𝑟][l,r] as points (𝑙,𝑟)(l,r) on a plane, build a Manhattan minimum spanning tree over all points, and transfer answers between queries along edges of this tree. This seems able to improve the time complexity of Mo's algorithm, but in fact the upper bound of the block-sorting method for queries is already optimal.

    Assume 𝑛,𝑚n,m are of the same order and 𝑛n is a perfect square. Consider intervals of the form [𝑎√𝑛,𝑏√𝑛](1 ≤𝑎,𝑏 ≤√𝑛)[an,bn](1≤a,b≤n); there are 𝑛n such intervals. If all intervals are viewed as points on a plane, the Manhattan distance between two points is exactly the transition cost between the two intervals, and the minimum Manhattan distance between any two intervals is √𝑛n. Therefore, the minimum time complexity for processing all queries is 𝑂(𝑛√𝑛)O(nn). Data constructions for other cases are similar.

    Mo's algorithm has another feature: when 𝑛n is fixed, the larger 𝑚m is, the smaller the average transition cost per query becomes. Some other offline algorithms also have this feature, such as Tarjan's algorithm for LCA, but Mo's algorithm has the most obvious change in average transition cost as 𝑚m changes.

    Examples and Code

    Example 「国家集训队」小 Z 的袜子

    Problem summary:

    There is a sequence {𝑐𝑖}{ci} of length 𝑛n. Given 𝑚m queries, each query gives two numbers 𝑙,𝑟l,r. Randomly choose two different numbers whose indices are between 𝑙l and 𝑟r, and find the probability that the two numbers are equal.

    Process

    Idea: this is a template problem for Mo's algorithm.

    For interval [𝑙,𝑟][l,r], sort in increasing order by the block number containing 𝑙l as the first key, and by 𝑟r as the second key.

    Then compute answers starting from the first query in the sequence. The first query is computed directly by brute force in 𝑂(𝑛)O(n) time, and later queries are answered based on the previous query.

    Detailed method:

    For interval [𝑖,𝑖][i,i], since it has only one element, the answer is easy to know. Then move step by step from the current interval (whose answer is known) toward the next interval.

    Let 𝑐𝑜𝑙[𝑖]col[i] denote how many times color 𝑖i appears currently, and let 𝑎𝑛𝑠ans denote the current number of feasible pairing schemes, i.e. the number of ways to choose a pair of socks with the same color. Then update the answer whenever moving: suppose the current color is 𝑘k. If the interval is expanded, add (𝑐𝑜𝑙[𝑘]+12) −(𝑐𝑜𝑙[𝑘]2)(col[k]+12)−(col[k]2) to 𝑎𝑛𝑠ans; if it is shrunk, subtract (𝑐𝑜𝑙[𝑘]2) −(𝑐𝑜𝑙[𝑘]−12)(col[k]2)−(col[k]−12) from 𝑎𝑛𝑠ans. The answer to this query is 𝑎𝑛𝑠(𝑟−𝑙+12)ans(r−l+12).

    There is an optimization here: (𝑎2) =𝑎(𝑎−1)2(a2)=a(a−1)2.

    Therefore (𝑎+12) −(𝑎2) =(𝑎+1)𝑎2 −𝑎(𝑎−1)2 =𝑎2 ⋅(𝑎 +1 −𝑎 +1) =𝑎2 ⋅2 =𝑎(a+12)−(a2)=(a+1)a2−a(a−1)2=a2⋅(a+1−a+1)=a2⋅2=a.

    So (𝑐𝑜𝑙[𝑘]+12) −(𝑐𝑜𝑙[𝑘]2) =𝑐𝑜𝑙[𝑘](col[k]+12)−(col[k]2)=col[k].

    Overall algorithm complexity: 𝑂(𝑛√𝑛)O(nn).

    In the code below, deno denotes the denominator of the answer, nume denotes the numerator, sqn denotes the block size √𝑛n, arr is the input array, node is the structure storing queries, tab is the query sequence after sorting, and col is as described above.

    Note: because of ++l and --r, the positions of the four while loops that move the interval in the code below are critical. Their relative order must not be changed arbitrarily.

    Discussion of the positions of the four loops

    Moving an interval in Mo's algorithm is equivalent to adding the elements of [1,𝑟][1,r] and deleting the elements of [1,𝑙 −1][1,l−1]. Therefore,

    • When 𝑙 ≤𝑟l≤r, the elements of [1,𝑙 −1][1,l−1] are effectively added once and deleted once, the elements of [𝑙,𝑟][l,r] are added once, and the elements of [𝑟 +1, +∞)[r+1,+∞) are not added. This is a valid interval.
    • When 𝑙 =𝑟 +1l=r+1, the elements of [1,𝑟][1,r] are effectively added once and deleted once, and the elements of [𝑟 +1, +∞)[r+1,+∞) are not added. This interval represents the empty interval.
    • When 𝑙 >𝑟 +1l>r+1, the elements of [𝑟 +1,𝑙 −1][r+1,l−1] (a nonempty interval) are deleted once but not added, so the number of times such an element has been added is negative.

    Therefore, if 𝑙 >𝑟 +1l>r+1 occurs at some moment, there will be an element whose addition count is negative. This causes problems in some tasks. For example, if we use a set to maintain all numbers in the interval, we may need to delete an element that does not exist in the set.

    The common feature of these 4 correct orders is that the first two steps expand the interval (l-- or r++), and the last two steps shrink it (l++ or r--). With this order, the first two steps expand the interval and keep 𝑙 ≤𝑟 +1l≤r+1. After the first two steps, 𝑙 ≤𝑙′ ≤𝑟′ ≤𝑟l≤l′≤r′≤r must hold. #include <cmath>
#include <iostream>
using namespace std;
constexpr int N = 50005;
int n, m, maxn;
int c[N];
long long sum;
int cnt[N];
long long ans1[N], ans2[N];

struct query {
  int l, r, id;

  bool operator<(const query &x) const {  // 重载<运算符
    if (l / maxn != x.l / maxn) return l < x.l;
    return (l / maxn) & 1 ? r < x.r : r > x.r;
  }
} a[N];

void add(int i) {
  sum += cnt[i];
  cnt[i]++;
}

void del(int i) {
  cnt[i]--;
  sum -= cnt[i];
}

long long gcd(long long a, long long b) { return b ? gcd(b, a % b) : a; }

int main() {
  cin.tie(nullptr)->sync_with_stdio(false);
  cin >> n >> m;
  maxn = sqrt(n);
  for (int i = 1; i <= n; i++) cin >> c[i];
  for (int i = 0; i < m; i++) cin >> a[i].l >> a[i].r, a[i].id = i;
  sort(a, a + m);
  for (int i = 0, l = 1, r = 0; i < m; i++) {  // 具体实现
    if (a[i].l == a[i].r) {
      ans1[a[i].id] = 0, ans2[a[i].id] = 1;
      continue;
    }
    while (l > a[i].l) add(c[--l]);
    while (r < a[i].r) add(c[++r]);
    while (l < a[i].l) del(c[l++]);
    while (r > a[i].r) del(c[r--]);
    ans1[a[i].id] = sum;
    ans2[a[i].id] = (long long)(r - l + 1) * (r - l) / 2;
  }
  for (int i = 0; i < m; i++) {
    if (ans1[i] != 0) {
      long long g = gcd(ans1[i], ans2[i]);
      ans1[i] /= g, ans2[i] /= g;
    } else
      ans2[i] = 1;
    cout << ans1[i] << '/' << ans2[i] << '\n';
  }
  return 0;
}

    By simulating manually, we find that the r pointer moves about 300 times. After processing the first block, 𝑙 =2,𝑟 =100l=2,r=100. At this point, only moving the l pointer twice would obtain the answer to the fourth query, but instead we move the r pointer to 1 to answer the third query, then move it back to 100 to answer the fourth query. This adds more than ninety pointer moves. How can we optimize this? Use odd-even sorting.

    What is odd-even sorting? For queries in odd-numbered blocks, sort r in increasing order; for queries in even-numbered blocks, sort r in decreasing order. Then after the r pointer finishes an odd block, it processes the even block on the way back, and then moves toward n to process the next odd block. This optimizes the number of moves of the r pointer. In general, this optimization can make the program about 30% faster.
